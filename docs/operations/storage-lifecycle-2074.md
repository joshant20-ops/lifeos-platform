# LifeOS storage lifecycle: evidence-first implementation (#2074)

The local inventory generated by the operator is metadata, not backup verification.
Existing policy authority: `docs/operations/records-retention.md`. Never use
age or directory names alone as permission to delete.

## Local-only read-only reports

From a checked-out review branch, after independent code review:

```bash
python3 scripts/lifeos_storage_retention_inventory.py ~/lifeos-storage-inventory.tsv
python3 -m scripts.lifeos_storage_backup_profile ~/lifeos-storage-inventory.tsv
python3 -m unittest tests.test_storage_retention_inventory tests.test_storage_backup_profile
```

The input inventory contains potentially sensitive file paths and must stay on
the Pi. The output contains only aggregate categories and age bands. No source
files are opened; neither script modifies storage. This report measures logical
file sizes, not actual ext4 allocated blocks or recoverable capacity.

## Protection requirements before ANY cleanup implementation

1. Identify producer and owning authority for each backup family and queue.
2. Prove a completed/terminal state from authoritative records, not a filename.
3. Verify the latest independent recovery point and restoration evidence.
4. Check rollback, open issue, incident, acceptance and minimum-retention holds.
5. Preserve unknown or ambiguous records; fail closed.
6. Obtain separate approval for a deterministic, audited deletion manifest.
7. Keep raw logs, private file names, paths and payloads off GitHub.
8. Do not alter AdGuard, DNS, Docker, running services or active log handles.

`storage-inspect-backup-evidence` currently inspects two fixed historical
evidence files; it does **not** validate the 69,063 backup groups or provide
general cleanup authority. Any new gateway operation requires its own review.

The May–August file modification spike is a historical clue, not proof that
backup creation is still healthy. Verify current backup schedules and restore
testing independently.

## Pi execution and Tier 0 gate

Use a reviewed immutable revision and the existing Watchman policy gate.
The fixed historical backup probe cannot run these new scripts. A canonical
command or an existing authorised local execution capability must be verified
before dispatch. Keep the inventory, command inputs and recovery records local.

Run `python3 -m governor.storage_tier0` with the configured household resolver,
a known local A record and its expected address, and an independently verified
public IP and TLS hostname. Pass these with `--resolver`, `--local-name`,
`--local-address`, `--internet-ip` and `--internet-name`. The probe checks AdGuard's
runtime state, DNS over UDP and TCP, a public DNS answer, direct IP TLS with
certificate validation, GitHub HTTPS and capacity on the AdGuard data mounts
and shared Docker filesystem. Reserve at least 10 GiB or 10% of capacity,
whichever is greater, and 10% of inodes as a provisional floor. Tune the floor
upward based on measured growth and recovery requirements. The baseline does
not grant maintenance permission. Independently prove a LAN client can resolve
through the household resolver, a local management session is usable, and the
offline recovery material is available. Record the results and GMT time locally.

Use the existing inventory with the commands above and run the targeted
Mosquitto probe via `python3 -m governor.read_only_storage_diagnostic --json`.
Run one diagnostic at a time at idle I/O priority and low CPU priority with
a supervised time and memory limit. Stop on pressure or connectivity loss.
A partial probe leaves the corresponding classification unknown. Compare
allocated blocks separately from logical bytes and never add Docker image and
containerd directory estimates as independent usage.

## Mosquitto rotation review

The operator measured 10,740,494,442 bytes in the current log and 188,920 bytes
of growth in 30 seconds. Writer identity remains unverified on Pi.
The GitHub-hosted ARM64 proof in run 42847652634 pulled the Compose digest,
identified Mosquitto 2.1.2 and demonstrated that its dedicated log-rotate
command reopened the log while the same subscriber continued to receive
messages. The rotated inode stopped growing and the broker process did not
restart. This used synthetic data and an isolated broker.

The read-only command `python3 -B -m governor.mqtt_rotation_preflight` checks the
running image, broker health and PID, expected log bind mount, regular file
identity and a writable descriptor on the same inode. It prints only check
booleans and bytes. Missing inspect or descriptor access blocks the check.
Run it only through a reviewed invocation with existing read access.

### Proposed live change for separate approval

- Scope the change to Mosquitto's current log and one uniquely named retained
  file in the same log directory. Confirm the exact image, inode, writer,
  ownership, permissions and sufficient disk and inode reserve immediately
  before acting. Prove household DNS from a LAN client, verify offline
  management and recovery access and confirm that there is no overlapping
  maintenance. Maintain local Tier 0 probes for the duration.
- Preserve the original log by same-filesystem rename, then request the
  broker's dedicated reopen command. Stop on any change of process identity,
  unexpected file or connectivity regression. Verify the new file is opened
  and grows, the old inode is closed and stable, and a representative MQTT
  client remains connected. Capture only sanitised status outside the Pi.
- If the rename succeeds but reopen fails, stop. Restore the original name
  only when it is absent and the broker still writes the retained inode.
  If both files exist or descriptor state is ambiguous, preserve both and
  investigate from the local console. Restarting the broker or changing
  AdGuard/network configuration is outside this proposal.
- Rotation retains both files and frees zero bytes. Verify archive integrity
  and restore from independent storage, and check incident, rollback and
  retention holds before proposing a separate disposal manifest.

The existing local submission socket authenticates the configured Engineer
UID. Repository access or self-hosted runner access does not prove access to
that socket. The fixed GitHub storage audit refreshes the root gateway and
does not run these checks. A reviewed dispatch via the existing Engineer /
Watchman path and live baseline evidence are required before approval for
the rotation itself.


## Independent AdGuard file restore drill

Use the existing private NFS4 backup mount. The drill checks the fixed mount
and holds its directory open, requires 4 GiB free and creates a unique mode
0700 staging directory. It copies the fixed historical AdGuard archive,
checks SHA-256 readback and gzip integrity, and restores files from the NAS
copy into a separate directory. Archive path, entry types, size and count
are checked before extraction. The copy and drill output stay private on the
NAS. Only status and numeric totals are returned. No DNS service is launched
from the restored files.

Run the reviewed source under the operator's existing NAS permissions using
`timeout 180s ionice -c3 nice -n 15 python3 -B -m governor.adguard_nas_restore_drill`.
Verify the share is private before dispatch. A result of file_restore_verified
proves recoverable files from the NAS copy, not a live resolver failover test.
Keep incomplete drill directories for local inspection and retention review.

The existing diagnostic queue is read-only. This drill creates backup files
on the NAS and needs an execution scope explicitly covering those writes.
The current Pi deployment and Watchman submission paths must not be repurposed
by labelling it a diagnostic or a control-state change. GitHub-hosted CI uses
only synthetic archives.
